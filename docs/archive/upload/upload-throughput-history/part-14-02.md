## 2026-03-06: shift root-cause focus from listener readiness to `reason=2` association churn

Problem:

- after host-side `wait_ready` polling cleanup, bounded acceptance no longer
  reproduced `listener_not_ready` / `listener_timeout`.
- the active failure shape in live logs shifted to repeated association churn:
  `failure_class=connect_timeout`, `failure_code=2`, with healthy scans still
  returning the target SSID and candidate set.
- artifact:
  - `logs/wifi_acceptance_waitready_hostcache_20260306_071601.log`
  - sample markers:
    - repeated `event scan_done ... count=11/12`
    - repeated `target_ssid=<test-ssid-primary> ... candidates=2`
    - repeated `event sta_disconnected reason=2 (other)`
    - no `listener_timeout` / `listener_not_ready` markers before stop.

Root-cause hypothesis:

- firmware `reason=2` recovery was still too eager to abandon a stable hinted
  BSSID:
  - observed-AP recovery could snap to another candidate even when the current
    hinted BSSID was still present.
  - after two `reason=2` hits it dropped the BSSID pin and rotated auth.
  - after three hits it hard-recovered before a bounded pinned auth/candidate
    sweep could complete.

Change:

- firmware now gives `reason=2` a bounded pinned-candidate sweep before broad
  recovery:
  - `src/firmware/storage/upload/wifi/connect/error/error_recovery/observed_ap.rs`
    - preserve current hinted BSSID for `reason=2` when it is still present in
      observed candidates.
    - rotate auth on that pinned candidate first.
    - only after pinned auth sweep exhaustion rotate to the next candidate or
      clear hints for discovery.
  - `src/firmware/storage/upload/wifi/connect/error.rs`
    - defer `reason=2` hard-recover escalation when the currently hinted BSSID
      is still observed, allowing the bounded pinned sweep to proceed.

Validation:

- `cargo check` passed after the change.
- code-file LOC policy remains satisfied:
  - `error.rs`: `300`
  - `observed_ap.rs`: `201`

Next:

- flash this variant and rerun bounded AP-contention acceptance / strict gate.
- success criteria:
  - fewer or no immediate `reason=2` snap-backs while hinted BSSID remains
    visible
  - evidence of bounded pinned auth sweep in logs
  - no regression of the already-hardened listener-readiness class.

## 2026-03-06: post-flash validation of `reason=2` pinned-sweep branch blocked by zero-discovery

Problem:

- after flashing the `reason=2` pinned-candidate sweep variant, immediate
  validation runs did not reach association churn.
- both acceptance boot-gate and standalone discovery debug fell back into
  all-zero discovery instead, so the new `reason=2` markers were never
  exercised on hardware.

Artifacts:

- acceptance boot-gate repro:
  - `logs/wifi_acceptance_reason2fix_20260306_072339.log`
- standalone discovery repro:
  - `logs/wifi_discovery_reason2fix_20260306_072522.log`

Observed:

- discovery stayed in `failure_class=discovery_empty`, `failure_code=201`.
- scan stages were all-zero across broad, directed, passive, and probe paths:
  - `scan_done status=0 count=0`
  - `result_count=0`
  - probe sweep also remained zero.
- no `reason=other preserving hinted candidate` markers appeared because
  association/connect was never reached.

Conclusion:

- the new `reason=2` hardening is implemented and flashed, but remains
  unvalidated in live AP-contention conditions.
- immediate blocker has shifted back to discovery blackout after flash; next
  useful action is to recover a non-zero discovery window first, then rerun the
  bounded acceptance probe to inspect the `reason=2` path.

## 2026-03-06: blackout localized to immediate post-start RX window

Objective:

- determine whether zero-discovery blackout appears only at scan entry or is
  already present immediately after `start_ok`, before the first scan path runs.

Change:

- added a new compile-time diagnostic hook:
  - `MEDITAMER_WIFI_POST_START_PROMISC_DIAG`
- implementation:
  - `src/firmware/storage/upload/wifi/connect/promisc_diag.rs`
    - refactor promiscuous sweep into a reusable helper
    - add `post_start_promisc_diag` entrypoint
  - `src/firmware/storage/upload/wifi/connect/mod.rs`
    - import new helper
  - `src/firmware/storage/upload/wifi/connect/prepare/prepare_start.rs`
    - invoke post-start promiscuous sweep immediately after `start_ok`,
      `set_power_saving(None)`, and protocol reapply, before scan progression.

Validation:

- flashed diagnostic build with:
  - `MEDITAMER_WIFI_POST_START_PROMISC_DIAG=1`
  - `ESPFLASH_PORT=/dev/cu.usbserial-510`
- bounded discovery run:
  - `logs/wifi_discovery_poststartpromisc_20260306_073128.log`

Observed:

- immediate post-start promiscuous RX was fully zero before first scan:
  - `post_start_promisc_diag window channel=8 ... total=0`
  - `post_start_promisc_diag window channel=1 ... total=0`
  - `post_start_promisc_diag window channel=6 ... total=0`
  - `post_start_promisc_diag window channel=11 ... total=0`
  - aggregate:
    `post_start_promisc_diag outcome=ok ... total=0 mgmt=0 ctrl=0 data=0 misc=0`
- only after that zero-RX post-start window did the first scan run, which was
  also all-zero:
  - `event scan_done status=0 count=0`
  - `scan_stage end label=active_broad ... result_count=0`

Conclusion:

- blackout is not just a scan-entry/result-marshaling issue.
- the radio RX path is already dark immediately after successful driver start,
  before the first staged scan runs.
- next root-cause target should move earlier than scan-entry handling:
  specifically start/recover sequencing and any deeper driver/radio reset path
  that can restore RX visibility after start.

## 2026-03-06: added early post-start blackout reset experiment

Objective:

- shorten recovery when the radio is already RX-black immediately after
  `start_ok`, instead of waiting through a full zero-discovery scan cycle.

Change:

- added compile-time knob:
  - `MEDITAMER_WIFI_SOFTWARE_RESET_ON_POST_START_PROMISC_ZERO`
- implementation:
  - `src/firmware/storage/upload/wifi/connect/promisc_diag.rs`
    - if `post_start_promisc_diag` completes with aggregate `total=0`, log
      `post_start_promisc_diag software_reset=true reason=post_start_promisc_zero`
      and trigger `esp_hal::system::software_reset()`
  - `tools/hostctl/src/workflows_wifi_discovery/probe.rs`
    - treat the new marker as expected soft-reset arming so discovery debug
      does not hard-fail on the immediate reboot

Validation:

- pending bounded discovery run with:
  - `MEDITAMER_WIFI_POST_START_PROMISC_DIAG=1`
  - `MEDITAMER_WIFI_SOFTWARE_RESET_ON_POST_START_PROMISC_ZERO=1`

Observed:

- flashed and ran bounded discovery with:
  - `logs/wifi_discovery_poststartreset_20260306_1r.log`
- first start hit the new marker:
  - `post_start_promisc_diag software_reset=true reason=post_start_promisc_zero`
  - followed by `BOOT_RESET reason=Some(CoreSw) code=3`
- host discovery workflow correctly recognized the marker and logged:
  - `expected_soft_reset_reboot_detected: reapplying NETCFG/NET START`
- after reboot and host re-provisioning, the firmware hit the same marker again:
  - second `post_start_promisc_diag software_reset=true ...`
  - second `BOOT_RESET reason=Some(CoreSw) code=3`
- the round then terminated because discovery workflow currently allows one
  expected soft-reset recovery per round.

Conclusion:

- immediate software reboot is not sufficient to break the blackout in this
  failing state; the post-start RX blackout reproduced again right after reboot.
- this shifts suspicion further away from in-process stop/start residue alone.
- next root-cause target should move lower or earlier:
  - board/radio bring-up invariants
  - boot/init-time Wi-Fi state
  - environment/hardware-level visibility issues that survive reboot

## 2026-03-06: capturable early driver-state pair added around first start

Objective:

- capture a before/after driver-state pair in the same round, before the first
  scan sequence, without relying on boot logs that host discovery may miss.

Change:

- added compile-time diagnostic hook:
  - `MEDITAMER_WIFI_EARLY_DRIVER_STATE_DIAG`
- implementation:
  - `src/firmware/storage/upload/wifi/connect/driver_state.rs`
    - one-shot `pre_start_driver_state`
    - one-shot `first_start_driver_state`
  - `src/firmware/storage/upload/wifi/connect/prepare/prepare_start.rs`
    - emit `pre_start_driver_state` immediately before first `start_async()`
    - emit `first_start_driver_state` immediately after first successful
      `start_ok`, before post-start promiscuous diagnostics

Validation:

- flashed with:
  - `MEDITAMER_WIFI_EARLY_DRIVER_STATE_DIAG=1`
  - `MEDITAMER_WIFI_POST_START_PROMISC_DIAG=1`
- bounded 1-round discovery capture:
  - `logs/wifi_discovery_earlystate_20260306_1r_c.log`

Observed:

- pre-start snapshot:
  - `pre_start_driver_state mode=1 primary=0 protocol_bitmap=0x07 cc=CN`
  - `max_tx_power_rc=12290`
  - `scan_defaults_rc=12295`
- first-start snapshot:
  - `first_start_driver_state mode=1 primary=1 protocol_bitmap=0x07 cc=CN`
  - `max_tx_power_rc=0 max_tx_power=80`
  - `scan_defaults_rc=0 scan_active_max=120 scan_passive=360 scan_home_dwell=30`
- immediately after the first-start snapshot, post-start promiscuous RX still
  remained fully zero across channels `8/1/6/11`.

Conclusion:

- the driver state looks materially more complete after `start_ok` than before
  start, which is expected.
- but once started, the visible post-start state is still coherent while RX is
  already blacked out.
- that further weakens the hypothesis that the failure is just an obviously bad
  runtime config or missing scan-default application.
