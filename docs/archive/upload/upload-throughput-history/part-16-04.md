## 2026-03-06: suppressing the `nan_dp_schedule_ndc_start` timer family removes the timer-side queue messages

- Added a default-off diagnostic gate in:
  - `vendor/esp-radio-0.17.0/src/compat/timer_compat.rs`
  - `src/firmware/storage/upload/wifi/connect/boot_scan_diag.rs`
- New knob:
  - `MEDITAMER_WIFI_SUPPRESS_NAN_DP_TIMER_ARM_DIAG=1`
- Behavior:
  - suppress only `ets_timer_arm[_us]` calls whose callback pointer falls inside the
    `nan_dp_schedule_ndc_start .. chm_mhz2num` symbol range
- Rebuilt, reflashed conservatively, and captured:
  - `logs/boot_scan_only_diag_nansuppress_20260306_berlin/boot_espflash_monitor.log`

Key evidence:
- suppression latched immediately:
  - after direct-IDF compare:
    - `suppressed_arm_count=1`
    - `last_suppressed_callback_ptr=0x401722d8`
    - `last_suppressed_arg_ptr=0x1`
  - after Rust scan:
    - `suppressed_arm_count=3`
    - `last_suppressed_callback_ptr=0x401722d8`
    - `last_suppressed_arg_ptr=0x1`
    - `last_suppressed_us=20000`
- address resolution still places `0x401722d8` in the `nan_dp_schedule_ndc_start` family
- the earlier timer-side dominant queue family disappears from the recent send ring:
  - no `task_role=timer item_word0=0x00000007 pointee_word0=0x00000008 ...`
  - recent queue sends are now only `main`-task `word0=6` ioctl objects and `wifi`-task
    `word0=0x00/0x10` items
- scan behavior changes materially:
  - direct-IDF compare: `scan_done_eventpost ... count=0 status=0 scan_id=0`
  - Rust scan: `elapsed_ms=8 result_count=0`
  - Rust scan event-post becomes `count=1 status=1 number=0 scan_id=129`

Conclusion:
- the `nan_dp_schedule_ndc_start` timer family is not incidental background noise; suppressing it
  materially changes the failure shape and removes the timer-side `(7,8,0|1)` queue traffic
- this is the strongest causal signal so far that the blackout is tied to this NAN/channel-scheduler
  timer family on the no-std `esp-radio` path
- the next step should be to understand why this timer family is active at all in the failing
  scan-only STA startup path, rather than keeping the suppression as a fix

## 2026-03-06: `chm_init` registers the `nan_dp_schedule_ndc_start` family twice, and suppressing only `arg=1` leaves the later `arg=0` timer path

- Static xref / bounded disassembly on the current build showed:
  - `chm_init` loads `0x401722d8` and calls the OSI timer-setfn hook twice
  - first registration:
    - timer object at `base + 36`
    - callback `0x401722d8`
    - arg `0`
  - second registration:
    - timer object at `base + 56`
    - callback `0x401722d8`
    - arg `1`
- Added a narrower default-off diagnostic gate:
  - `MEDITAMER_WIFI_SUPPRESS_NAN_DP_TIMER_ARG1_ARM_DIAG=1`
- Rebuilt, reflashed, and captured:
  - `logs/boot_scan_only_diag_nanarg1_20260306_berlin/boot_espflash_monitor.log`

Key evidence:
- with only `arg=1` suppressed:
  - direct-IDF compare still shifts to the altered early-fail shape:
    - `scan_done_eventpost after=idf_compare_first count=0 status=0 scan_id=0`
  - Rust scan still fails early:
    - `scan=ok elapsed_ms=8 result_count=0`
    - `scan_done_eventpost after=rust_scan count=1 status=1 number=0 scan_id=129`
- but the later timer-side queue family is not fully gone:
  - recent sends still include:
    - `task_role=timer item_word0=0x00000007 pointee_word0=0x00000008 pointee_word1=0x00000000 timer_callback_ptr=0x40172290 timer_arg_ptr=0x0`
- timer arm history now clearly alternates the two registrations:
  - `callback_ptr=0x40172290 arg_ptr=0x1 us=20000`
  - `callback_ptr=0x40172290 arg_ptr=0x0 us=10000`
  - `suppressed_arm_count=14` shows the `arg=1` branch is being actively suppressed, while the
    `arg=0` branch still arms and executes

Conclusion:
- the `arg=1` branch is sufficient to trigger the early altered failure shape
- the `arg=0` branch is still responsible for the later surviving `(7,8,0)` timer-side queue
  traffic when only `arg=1` is suppressed
- this splits the problem into two branches registered by `chm_init`:
  - `arg=1` correlates with the earlier `(7,8,1)` / direct-IDF-compare phase
  - `arg=0` correlates with the later `(7,8,0)` / Rust-scan phase

## 2026-03-06: suppressing only `arg=0` leaves the original `(7,8,1)` timer traffic and original failure shape

- Added the symmetric default-off knob:
  - `MEDITAMER_WIFI_SUPPRESS_NAN_DP_TIMER_ARG0_ARM_DIAG=1`
- Rebuilt, reflashed, and captured:
  - `logs/boot_scan_only_diag_nanarg0_20260306_berlin/boot_espflash_monitor.log`

Key evidence:
- with only `arg=0` suppressed:
  - direct-IDF compare keeps the earlier original shape:
    - `idf_compare=ok ... ap_num=0`
    - `scan_done_eventpost after=idf_compare_first count=1 status=0 scan_id=128`
  - timer-side queue traffic remains dominated by the `arg=1` branch:
    - `task_role=timer item_word0=0x00000007 pointee_word0=0x00000008 pointee_word1=0x00000001 timer_callback_ptr=0x401722ac timer_arg_ptr=0x1`
  - Rust scan also keeps the earlier original shape:
    - `elapsed_ms=309 result_count=0`
    - `scan_done_eventpost after=rust_scan count=2 status=0 number=0 scan_id=129`
- suppression is active, but only on the `arg=0` branch:
  - `suppressed_arm_count=13`
  - `last_suppressed_arg_ptr=0x0`
  - recent arm ring still alternates the two branches, with `arg=1` arms surviving at `20000 us`

Conclusion:
- suppressing `arg=0` alone does not materially disrupt the original blackout shape
- by contrast, suppressing `arg=1` alone was enough to shift the failure shape early
- therefore the `arg=1` branch is the dominant causal branch, while `arg=0` is secondary and
  mostly explains the later surviving timer traffic

## 2026-03-06: suppressing only the `arg=1` registration at `setfn` reproduces the dominant branch effect

- Added a default-off registration-time diagnostic gate:
  - `MEDITAMER_WIFI_SUPPRESS_NAN_DP_TIMER_ARG1_SETFN_DIAG=1`
- Implementation:
  - when `compat_timer_setfn` sees the `nan_dp_schedule_ndc_start` family with `arg=1`,
    it still creates a timer object but substitutes a no-op callback instead of the original
    callback, preserving later arm structure without the original handler body
- Rebuilt, reflashed, and captured:
  - `logs/boot_scan_only_diag_nanarg1setfn_20260306_berlin/boot_espflash_monitor.log`

Key evidence:
- registration suppression latched:
  - `suppressed_setfn_count=1`
  - `last_suppressed_setfn_callback_ptr=0x401722d0`
  - `last_suppressed_setfn_arg_ptr=0x1`
- direct-IDF compare shifts to the same altered early shape seen with `arg=1` arm suppression:
  - `scan_done_eventpost after=idf_compare_first count=0 status=0 scan_id=0`
- Rust scan also matches the altered early shape:
  - `scan=ok elapsed_ms=8 result_count=0`
  - `scan_done_eventpost after=rust_scan count=1 status=1 number=0 scan_id=129`
- timer-side queue traffic after the Rust scan now only shows the surviving `arg=0` branch:
  - `task_role=timer item_word0=0x00000007 pointee_word0=0x00000008 pointee_word1=0x00000000 timer_arg_ptr=0x0`
- recent arm ring still contains both handles structurally, but only the `arg=0` branch retains
  the original callback body; the `arg=1` timer was neutered at registration time

Conclusion:
- the dominant causal branch is pinned at registration time, not only at re-arm time
- suppressing the `arg=1` `setfn` alone reproduces the same major shape change as suppressing the
  `arg=1` arms later
- this is the strongest evidence so far that the real problem enters when `chm_init` registers the
  `arg=1` `nan_dp_schedule_ndc_start` timer in this no-std startup path

## 2026-03-06: wrapper-arm caller trace pins both surviving timer arm sites inside `chm_init`

- Extended the timer diagnostics to record the caller PC at the Rust wrapper boundary
  (`common_adapter::ets_timer_arm[_us]`), not only inside `compat_timer_arm_us`.
- Rebuilt, reflashed with the existing `arg=1` registration suppression, and captured:
  - `logs/boot_scan_only_diag_nanarg1setfn_wrappercallers_20260306_berlin/boot_espflash_monitor.log`

Key evidence:
- the new wrapper-arm ring is populated and stable:
  - `wrapper_arm_count=27`
  - repeated wrapper caller PCs alternate between:
    - `caller_ptr=0x80172fb5 us=20000`
    - `caller_ptr=0x80172f85 us=10000`
- the lower compat-layer caller still stays at the generic Rust wrapper return site:
  - `timer_compat_arm_recent ... caller_ptr=0x801420e5`
  - so the wrapper trace is the useful discriminator
- symbol/disassembly resolution against the current ELF places both wrapper return PCs inside
  `chm_init`:
  - `0x80172f85` is the return point after the first OSI timer-arm call in `chm_init`
    (`callx8` at `0x40172f71`)
  - `0x80172fb5` is the return point after the second OSI timer-arm call in `chm_init`
    (`callx8` at `0x40172fa1`)
- the same bounded run still preserves the already-known dominant-branch behavior:
  - `idf_compare_first scan_done_eventpost count=0 status=0 scan_id=0`
  - Rust scan `elapsed_ms=8 result_count=0`
  - Rust scan event-post `count=1 status=1`

Conclusion:
- the surviving timer arm traffic is not coming from a later generic timer worker
- both arm sites are issued directly from `chm_init` itself
- this tightens the root-cause target further:
  - `chm_init` is both the registration site for the dominant `arg=1` branch and the direct arm
    site for the alternating `10000/20000 us` branches
- the next diagnostic target should move one step earlier than timer machinery:
  - identify why this no-std startup path reaches the `chm_init` NAN/channel-manager setup in a
    state that produces the zero-scan failure, and compare that precondition path against the
    working Rust-on-IDF and C/ESP-IDF controls

## 2026-03-06: static call-chain check rejects “explicit `nan_start` in STA path” and pins `chm_init` to normal `wifi_hw_start`

- Performed static disassembly on the current debug ELF rather than another live probe.

Key evidence:
- `wifi_start_process` drives the normal start flow:
  - `wifi_start_process (0x40181708)` calls `wifi_mode_set`
  - then `_do_wifi_start (0x4017f528)`
- `_do_wifi_start` only calls `nan_start (0x40173adc)` when mode `== 4`:
  - branch at `0x4017f5d8`
  - `call8 40173adc <nan_start>` at `0x4017f5de`
- in the STA path, `_do_wifi_start` instead takes the net80211 STA-create function-pointer path:
  - function-pointer call at `0x4017f5bf`
  - explicit `nan_start` is not on the mode-1 STA branch
- separately, `chm_init` is called directly from `wifi_hw_start`, not from `nan_start`:
  - `wifi_hw_start` calls:
    - `wifi_reset_mac` at `0x40180d87`
    - `ic_mac_init` at `0x40180d8d`
    - `chm_init` at `0x40180d95`
    - `chip_enable` at `0x40180da1`
- `wifi_hw_start` is used by generic start/mode paths, including `wifi_set_promis_process`
  and related mode transitions, so `chm_init` is part of ordinary Wi-Fi hardware bring-up in this
  blob, not a uniquely explicit NAN-start side branch

Conclusion:
- the simple hypothesis “STA startup is accidentally calling explicit `nan_start`” is rejected
- the stronger remaining hypothesis is:
  - normal Wi-Fi hardware start (`wifi_hw_start`) enters `chm_init` with preconditions/state that
    later trigger the dominant `arg=1` registration and zero-scan behavior in this no-std runtime
- the next diagnostic step should focus on the state handed into `wifi_hw_start` / `chm_init`
  during STA startup, not on the explicit `nan_start` path

## 2026-03-06: raw blob-state probe shows `g_chm` active-op/current-channel state mutates while `g_ic` / STA state stay stable across the failing window

- Added a narrow raw-state diagnostic helper for the specific globals/offsets touched by
  `wifi_hw_start`, `wifi_station_start`, and `chm_init`:
  - `g_ic`
  - current STA object (`g_ic + 0x10`)
  - `g_chm` slot and pointed channel-manager object
- Rebuilt, reflashed, and captured:
  - `logs/boot_scan_only_diag_blobstate_20260306_berlin_retry1/boot_espflash_monitor.log`

Key evidence:
- direct-IDF compare still fails in the same altered early shape:
  - `scan_done_eventpost after=idf_compare_first count=0 status=0 scan_id=0`
- Rust scan still fails immediately afterward:
  - `scan=ok elapsed_ms=8 result_count=0`
  - `scan_done_eventpost after=rust_scan count=1 status=1 number=0 scan_id=129`
- `g_ic` and STA-object snapshots stay stable across the two failing checkpoints:
  - `flags_251=0x01 flags_252=0x01`
  - `ptr_130=0x0 ptr_134=0x3ffd327c ptr_1b4=0x3ffbda0c`
  - STA object:
    - `flag_154=0x00`
    - `flag_155=0x02`
    - `val_15e=0x0000`
- static field mapping of the current blob corrects the `g_chm` interpretation:
  - `+0x04/+0x05` are the active operation channel/mode slot set by `chm_start_op`
  - `+0x50/+0x51` are the home channel/mode pair
  - `+0x52/+0x53` are the current channel/mode pair updated by `chm_set_current_channel`
- reinterpreting the captured raw bytes from the successful live probe:
  - after `idf_compare_first`:
    - active op: `op_chan=0x01 op_mode=0x00`
    - op metadata: `ptr_08=0x0 ptr_0c=0x78`
    - current channel: `current_chan=0x01 current_mode=0x00`
  - after `rust_scan`:
    - active op: `op_chan=0x04 op_mode=0x00`
    - op metadata: `ptr_08=0x0a ptr_0c=0x14`
    - current channel: `current_chan=0x04 current_mode=0x00`
  - `ptr_10` / `ptr_14` remain stable across both snapshots
- a follow-up flash with corrected field labels was attempted, but the flash phase stalled before
  completion, so the semantic correction above is derived from static disassembly plus the earlier
  successful raw-byte capture

Conclusion:
- the failing window is not explained by gross instability in the top-level `g_ic` object or STA
  object creation
- the most material evolving state is inside the channel-manager object behind `g_chm`
- specifically, the active-op slot and current-channel pair advance from channel `1` to channel `4`
  while scan visibility is still zero
- this strengthens the current target:
  - the no-std blackout is likely tied to bad `chm` state evolution across the earliest scan path,
    not to missing STA allocation or a generic Wi-Fi object initialization failure
- the next step should trace why the no-std path advances the channel manager from channel `1` to
  channel `4` in this early failing window, and compare that channel/op progression against the
  working IDF controls
