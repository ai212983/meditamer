## 2026-03-06: stable host-side flash dump profile recovered full `nvs` reads

Objective:

- determine whether raw `nvs` inspection is actually unreliable or whether the
  earlier failures were caused by aggressive `espflash read-flash` defaults.

Change:

- validated a conservative raw-read transport profile:
  - `ESPFLASH_BAUD=115200`
  - `--block-size 0x100`
  - `--max-in-flight 1`
- added repo-local helper:
  - `scripts/device/dump_wifi_partitions.sh`

Validation:

- probe reads succeeded for:
  - `nvs` first `0x100` bytes
  - `nvs` first `0x1000` bytes
  - full `nvs` region (`0x9000`, `0x6000`)
- first `0x100` bytes decode as valid-looking NVS page content rather than all
  `0xff`

Observed:

- the prior `corrupt_data expected ... received ...` failures were transport
  tuning failures, not proof that `nvs` itself was unreadable.
- stable full-region `nvs` dumps are now achievable with the conservative
  profile, so lower-level flash inspection is a viable path again.

Conclusion:

- raw `nvs` inspection is now a stable primary diagnostic path, provided the
  helper/read profile is used.
- the next lower-level task should use the new repo-local dump helper to
  compare blackout vs known-good flash-state artifacts instead of relying on
  ad hoc shell commands.

## 2026-03-06: same-device post-erase baseline and blank-state discovery check

Objective:

- obtain a same-device baseline without a second board and verify whether blank
  persisted Wi-Fi state changes the discovery blackout behavior.

Procedure:

- captured pre-erase checkpoint with:
  - `scripts/device/dump_wifi_partitions.sh`
- erased only:
  - `nvs` at `0x9000` length `0x6000`
  - `phy_init` at `0xf000` length `0x1000`
- reflashed the same debug firmware with:
  - `ESPFLASH_PORT=/dev/cu.usbserial-510`
  - `FLASH_SET_TIME_AFTER_FLASH=0`
- captured immediate post-flash dump
- ran bounded 1-round discovery from the blank state
- captured post-run dump again

Artifacts:

- sequence root:
  - `logs/flash_dumps/baseline_sequence_20260306_083148`
- pre-erase summary:
  - `logs/flash_dumps/baseline_sequence_20260306_083148/pre/wifi_partitions_checkpoint/summary.txt`
- post-erase/reflash summary:
  - `logs/flash_dumps/baseline_sequence_20260306_083148/post/wifi_partitions_after_erase_reflash/summary.txt`
- post-run summary:
  - `logs/flash_dumps/baseline_sequence_20260306_083148/post_run/wifi_partitions_after_blank_discovery/summary.txt`
- bounded discovery log:
  - `logs/flash_dumps/baseline_sequence_20260306_083148/discovery_after_blank_1r.log`

Observed:

- pre-erase persisted-state MD5s:
  - `nvs`: `0x1a649b535a4ae08d173a738eae0bc8eb`
  - `phy_init`: `0xf34b8a303a528ee681ef6c943b6c09e0`
- immediate post-erase/reflash MD5s changed to:
  - `nvs`: `0x5c65ae66b72ed07bba39174eb31762ed`
  - `phy_init`: `0x6ae59e64850377ee5470c854761551ea`
- first-page hexdumps after erase/reflash were fully erased (`0xff`) for both
  `nvs` and `phy_init`, so the device now has a true blank persisted-state
  baseline.
- the blank-state bounded discovery run still reproduced
  `failure_class="discovery_empty"` with zero-result scans.
- post-run dump MD5s were unchanged from the blank post-erase state:
  - `nvs`: `0x5c65ae66b72ed07bba39174eb31762ed`
  - `phy_init`: `0x6ae59e64850377ee5470c854761551ea`

Conclusion:

- the discovery blackout reproduces even when both `nvs` and `phy_init` start
  from a blank erased state.
- the failing bounded discovery path does not repopulate those persisted
  regions, so the blackout is not explained by bad leftover Wi-Fi persisted
  state in those partitions.
- this shifts the remaining root-cause focus further away from flash-persisted
  Wi-Fi config and toward runtime radio/driver bring-up or another non-persisted
  state path.

## 2026-03-06: first `NET START` from initial waiting state still blackouts

Objective:

- remove host recovery/restart churn from the sequence and check whether the
  blackout already exists on the first Wi-Fi start issued from the app's idle
  `waiting for NETCFG credentials` state.

Procedure:

- flashed diagnostic build with:
  - `MEDITAMER_WIFI_EARLY_DRIVER_STATE_DIAG=1`
  - `MEDITAMER_WIFI_POST_START_PROMISC_DIAG=1`
  - `MEDITAMER_WIFI_SOFTWARE_RESET_ON_POST_START_PROMISC_ZERO=0`
  - `MEDITAMER_WIFI_POST_START_PROMISC_ZERO_HARD_REINIT=0`
- captured clean boot with `espflash monitor`:
  - `logs/boot_runtime_diag_20260306_083904/boot_espflash_monitor.log`
- confirmed app reached:
  - `upload_http: waiting for NETCFG credentials over UART`
- from that waiting state, used direct UART control (not hostctl discovery
  workflow) to send:
  - `STATE SET upload=on`
  - `NET LISTENER OFF`
  - `NETCFG SET {...}`
  - `NET START`
  - periodic `NET STATUS`
- captured the live transcript in:
  - `logs/boot_runtime_diag_20260306_083904/start_from_waiting.raw.log`

Observed:

- boot itself is normal; the app starts and reaches runtime upload waiting state
  on blank `nvs`/`phy_init`.
- on the first `NET START` from `Idle`:
  - `pre_start_driver_state` still has partially invalid pre-start getters
  - `first_start_driver_state` becomes coherent after `start_ok`
  - `first_start_sta_config` is sane and matches the expected SSID/auth setup
- immediately after `start_ok`, before any prior host recover loop:
  - `post_start_promisc_diag ... total=0` on channels `8/1/6/11`
- the first scan sequence then also starts from zero:
  - `scan active_broad found=0`
  - `scan active_directed found=0`
  - passive stage proceeds from the same zero-candidate state

Conclusion:

- the blackout is not caused by hostctl recovery churn, repeated `NET RECOVER`,
  or reboot-to-recover loops.
- it reproduces on the first Wi-Fi start from the app's clean waiting state on
  blank persisted flash.
- that narrows the primary target further to runtime radio/RX bring-up on first
  start rather than state carry-over from earlier workflow activity.

## 2026-03-06: first-start raw broad scan is also zero on blank-state idle start

Objective:

- confirm whether the immediate raw broad scan bypass is also zero in the same
  blank-state, first-start-from-idle scenario, not just in earlier historical
  runs.

Procedure:

- flashed diagnostic build with:
  - `MEDITAMER_WIFI_EARLY_DRIVER_STATE_DIAG=1`
  - `MEDITAMER_WIFI_POST_START_PROMISC_DIAG=1`
  - `MEDITAMER_WIFI_START_RAW_SCAN_DIAG=1`
  - recovery variants still off
- captured clean boot:
  - `logs/boot_runtime_diag_rawscan_20260306_084548/boot_espflash_monitor.log`
- from `waiting for NETCFG credentials over UART`, sent the same direct UART
  first-start sequence and captured:
  - `logs/boot_runtime_diag_rawscan_20260306_084548/start_from_waiting.raw.log`

Observed:

- the same clean first-start path again showed:
  - coherent `first_start_driver_state`
  - `post_start_promisc_diag ... total=0`
- the new immediate raw broad scan bypass also returned zero before normal scan
  staging:
  - `start_raw_scan_diag outcome=ok elapsed_ms=221 result_count=0 top_channel=0 top_bssid=<none>`
- normal scan flow then continued from the same zero-result state.

Conclusion:

- on the blank-state device, first-start blackout is already visible in all
  three layers:
  - post-start promiscuous RX sweep
  - immediate raw broad scan bypass
  - normal staged scan path
- this further weakens any remaining “scan wrapper/staging” explanation for the
  clean-start blackout and keeps the root-cause target on runtime radio/RX
  bring-up below the high-level scan path.

## 2026-03-06: scoped Wi-Fi internal log bump did not reveal a new lower-level signal

Objective:

- raise Wi-Fi internal driver logging only across the first-start window and
  check whether that surfaces an additional lower-level clue before the already
  observed zero raw scan.

Change:

- added compile-time diagnostic knob:
  - `MEDITAMER_WIFI_FIRST_START_IDF_LOG_DIAG`
- behavior:
  - set Wi-Fi internal log level to `DEBUG` immediately after first `start_ok`
  - restore `INFO` on the first `scan_done`
- also added explicit event logs for:
  - `WifiReady`
  - `StaAuthmodeChange`
  - `StaBeaconTimeout`

Artifacts:

- boot:
  - `logs/boot_runtime_diag_idflog_20260306_085344/boot_espflash_monitor.log`
- first-start transcript:
  - `logs/boot_runtime_diag_idflog_20260306_085344/start_from_waiting.raw.log`

Observed:

- the scoped bump path worked:
  - `first_start_idf_log_diag set_rc=0 target_level=4`
  - `first_start_idf_log_diag_restore reason=scan_done restore_level=3 set_rc=0`
- despite that, the same clean-start sequence still showed:
  - coherent `first_start_driver_state`
  - `post_start_promisc_diag ... total=0`
  - `start_raw_scan_diag outcome=ok ... result_count=0`
- no new `StaBeaconTimeout` or `StaAuthmodeChange` signal appeared before the
  zero raw scan / zero staged scan sequence in this capture.

Conclusion:

- the scoped internal Wi-Fi log bump is a valid reusable diagnostic tool, but
  on this run it did not expose a new lower-level cause before the blackout.
- the root-cause target remains runtime radio/RX bring-up below the normal scan
  path, with current evidence still pointing to “started and configured, but RX
  dark immediately after first start.”
