## 2026-03-06: the observed `g_chm` active-op record matches the scan path (`clear_bss_queue -> chm_start_op`), not the direct NAN/NDC caller

- Continued static disassembly on the current ELF to classify the active-op metadata captured in:
  - `logs/boot_scan_only_diag_blobstate_20260306_berlin_retry1/boot_espflash_monitor.log`
- Relevant symbols in the current build:
  - `chm_start_op = 0x4017343c`
  - `clear_bss_queue = 0x4017638c`
  - `scan_inter_channel_timeout_process = 0x40176854`
  - `nan_dp_indicate_ndc_start = 0x40172b1c`
  - `app_scan_params = 0x3ffd3ba8`
  - `connect_scan_flag = 0x3ffd3ba4`
- `chm_start_op` stores the caller-provided metadata directly into the active-op record:
  - `+0x08 <- a3`
  - `+0x0c <- a4`
  - `+0x10 <- a7`
  - `+0x14 <- a5`
  - `+0x18 <- a6`
- The direct NAN/NDC caller (`nan_dp_indicate_ndc_start`) passes:
  - `a3 = 0`
  - `a4 = 16`
  - `a5 = callback 0x40170fc0`
  - `a6 = lock/context pointer 0x40170fa4`
  - `a7 = 0`
- The scan path through `clear_bss_queue` passes a materially different shape:
  - `a3 = scan-state scalar`
  - `a4 = dwell/timeout scalar`
  - `a5 = scan callback near 0x40174858`
  - `a6 = follow-up handler 0x401768d8`
  - `a7 = scan-local context pointer near the `app_scan_params` / `connect_scan_flag` region
- That matches the retry1 live capture much better than the NAN/NDC path:
  - stable callback-like `ptr_14` near the scan callback region
  - stable context-like `ptr_10` in the scan globals neighborhood
  - small scalar metadata in `ptr_08` / `ptr_0c`
- `scan_inter_channel_timeout_process` also calls back into `clear_bss_queue`, which is consistent
  with the observed `current_chan` advance from `1` to `4` during the still-blacked-out window.

Conclusion:
- the strongest current interpretation is no longer “the blackout is driven by direct NAN/NDC
  channel start”
- the observed `g_chm` record is much more consistent with ordinary scan channel-manager
  progression through `clear_bss_queue -> chm_start_op`
- so the root-cause focus should move from “why does `nan_dp_indicate_ndc_start` run” to:
  - why the no-std scan path enters this channel-manager progression in a state that yields
    `ScanDone(count=0)`
  - and whether the scan callback/context pair recorded in `g_chm` diverges semantically from the
    working IDF paths
- note: the source-side label fix in `blob_state_diag.rs` is already applied locally, but the board
  is still on the last successful retry1 image because the follow-up reflash stalled before
  completion

## 2026-03-06: both retry1 `g_chm` active-op snapshots can be explained by the same scan caller without invoking any nonzero `coex_status_get` path

- Continued static disassembly of `clear_bss_queue` and `scan_inter_channel_timeout_process`
  against the retry1 live `g_chm` record.
- Also resolved the exact ESP32 `wifi_osi_funcs_t` layout from the generated `esp-wifi-sys`
  bindings:
  - `g_osi_funcs_p + 0x194 = _coex_status_get`
- Disassembly of the compiled vendored adapter function confirms the current image uses the
  non-`coex` stub:
  - `esp_radio::wifi::os_adapter::coex_status_get`
  - returns constant `0`
- In the current build, `clear_bss_queue` selects channel timing values before calling
  `chm_start_op`:
  - if `ieee80211_regdomain_is_active_scan(chan)` returns true:
    - `a4 <- scan_struct + 52`
    - `a2 <- scan_struct + 48`
  - otherwise:
    - `a4 <- g_ic + 56`
    - `a2 <- a4`
- The same call site then has two materially different outcomes:
  - the `g_osi_funcs_p + 0x194` callback is not a mixed branch source here:
    - it is `coex_status_get`
    - in this image it always returns `0`
  - so the live scalar differences must come from the selected dwell/timing inputs themselves,
    not from a nonzero/zero split at `_coex_status_get`
- Because `chm_start_op` stores:
  - `+0x08 <- a11`
  - `+0x0c <- a12`
  both retry1 snapshots are still consistent with this single scan caller:
  - `idf_compare_first`: `ptr_08=0x0 ptr_0c=0x78`
    - matches a scan state where the selected operation metadata already supplies
      zero/`0x78`-like scalars
  - `rust_scan`: `ptr_08=0x0a ptr_0c=0x14`
    - matches a later scan state where the selected operation metadata supplies
      `0x0a/0x14`-like dwell/channel-step scalars
- `scan_inter_channel_timeout_process` feeds back into `clear_bss_queue`, so this is also
  consistent with the live `current_chan` advance from `1` to `4` without requiring any different
  direct `chm_start_op` caller.

Conclusion:
- the retry1 `g_chm` mutation no longer needs two different explanations
- both the early `0/0x78` record and the later `0x0a/0x14` record fit the same ordinary scan
  progression path through `clear_bss_queue`
- `coex_status_get` is no longer a credible primary target for this split, because the compiled
  no-`coex` adapter returns constant `0`
- the strongest remaining root-cause target is now the source of the selected scan dwell/channel
  scalars feeding `clear_bss_queue` and the resulting scan/channel-manager progression semantics on
  the no-std path, not the identity of the `chm_start_op` caller itself

## 2026-03-06: IDF-like explicit scan timing changes the no-std `g_chm` path, but still does not recover AP visibility

- Added a guarded vendored `esp-radio` scan-timing A/B in:
  - `vendor/esp-radio-0.17.0/src/wifi/mod.rs`
- New build-time knob:
  - `MEDITAMER_WIFI_ESP_RADIO_USE_IDF_DEFAULT_SCAN_TIMING_DIAG=1`
- This changes only the wrapper default active broad-scan timing when the wrapper is still using
  its stock `10/20 ms` defaults:
  - active min `10 -> 0`
  - active max `20 -> 120`
  - home-channel dwell `0 -> 30`
- Rebuilt and ran the bounded boot scan with:
  - `MEDITAMER_WIFI_BOOT_SCAN_ONLY_DIAG=1`
  - `MEDITAMER_WIFI_BOOT_SCAN_ONLY_DIAG_IDF_NULL_FIRST=1`
  - `MEDITAMER_WIFI_ESP_RADIO_USE_IDF_DEFAULT_SCAN_TIMING_DIAG=1`
- Captured:
  - `logs/boot_scan_only_diag_idfscantiming_20260306_berlin.log`

Key evidence from the log:
- driver defaults confirm the override latched:
  - `scan_active_min=0 scan_active_max=120 scan_passive=360 scan_home_dwell=30`
- the direct IDF null-config comparator in the same no-std image still fails first:
  - `event scan_done status=0 count=0 scan_id=128`
  - `boot_scan_only_diag idf_compare=ok ... ap_num=0`
- unlike the earlier retry1 shape, `g_chm` no longer progresses through the visible active-op
  scan state:
  - after `idf_compare_first`:
    - `op_chan=0xff op_mode=0x00 ptr_08=0x0 ptr_0c=0x0 ptr_10=0x0 ptr_14=0x0`
    - `home_chan=0x01 current_chan=0x01`
  - after `rust_scan`:
    - `op_chan=0xff op_mode=0x00 ptr_08=0x0 ptr_0c=0x0 ptr_10=0x0 ptr_14=0x0`
    - `home_chan=0x01 current_chan=0x01`
- despite that materially different internal path shape, the wrapped Rust scan still fails:
  - `event scan_done status=0 count=0 scan_id=129`
  - `boot_scan_only_diag scan=ok elapsed_ms=1604 result_count=0`

Conclusion:
- making the wrapper broad-scan timing IDF-like is causally relevant to the earlier `g_chm`
  progression shape
- but it is not sufficient to recover AP visibility on the no-std path
- the remaining boundary is therefore tighter:
  - not just scan dwell/home-dwell values
  - likely the broader explicit-scan command path / pre-scan runtime state that still differs from
    the working C and Rust-on-IDF controls

## 2026-03-07: direct IDF explicit broad scan also fails in the no-std image, so `NULL` vs explicit scan config is not the remaining discriminator

- Added a boot-only direct IDF explicit-scan comparator in:
  - `src/firmware/storage/upload/wifi/connect/boot_scan_idf_compare.rs`
- Wired it through:
  - `src/firmware/storage/upload/wifi/connect/boot_scan_diag.rs`
  - `src/firmware/storage/upload/wifi/connect/mod.rs`
- New build-time knob:
  - `MEDITAMER_WIFI_BOOT_SCAN_ONLY_DIAG_IDF_EXPLICIT_COMPARE=1`
- The comparator runs, in the same no-std image and same started STA session:
  1. direct IDF `esp_wifi_scan_start(NULL, true)`
  2. direct IDF explicit active broad scan with the same broad config shape as the wrapper
  3. wrapped `esp-radio` broad scan
- To bypass the recurring `espflash flash` transport stall, generated a merged image with:
  - `espflash save-image --chip esp32 --merge target/xtensa-esp32-none-elf/debug/meditamer ...`
- Then flashed successfully via:
  - external `esptool.py write_flash -z 0x0 target/xtensa-esp32-none-elf/debug/meditamer-merged.bin`
- Captured bounded log:
  - `logs/boot_scan_only_diag_idfexplicit_esptool_20260307_berlin.log`

Key evidence from the log:
- driver state still shows the IDF-like timing override latched:
  - `scan_active_min=0 scan_active_max=120 scan_passive=360 scan_home_dwell=30`
- direct IDF `NULL` scan still fails first:
  - `event scan_done status=0 count=0 scan_id=128`
  - `boot_scan_only_diag idf_compare=ok ... ap_num=0`
- direct IDF explicit broad scan with the same broad active config also fails:
  - `boot_scan_only_diag idf_explicit_compare begin=true active_min_ms=0 active_max_ms=120 passive_ms=0 home_chan_dwell_ms=30 show_hidden=true channel=0`
  - `event scan_done status=0 count=0 scan_id=129`
  - `boot_scan_only_diag idf_explicit_compare=ok ... ap_num=0`
- wrapped Rust broad scan still fails afterward:
  - `event scan_done status=0 count=0 scan_id=130`
  - `boot_scan_only_diag scan=ok elapsed_ms=1608 result_count=0`
- the flattened `g_chm` shape remains unchanged across all three scans:
  - after `idf_compare_first`: `op_chan=0xff ... current_chan=0x01`
  - after `idf_explicit_compare_first`: `op_chan=0xff ... current_chan=0x01`
  - after `rust_scan`: `op_chan=0xff ... current_chan=0x01`

Conclusion:
- the remaining no-std blackout is **not** explained by:
  - wrapper-vs-direct scan API usage
  - `NULL` vs explicit broad scan config
  - active broad scan timing/home-dwell values alone
- all three scan entry variants now fail identically in the no-std image while the same board still
  has working C/ESP-IDF and Rust-on-IDF controls from earlier validation
- the next root-cause target should therefore move below scan-call selection and back to the
  no-std runtime/driver state that exists before the first scan command is issued

## 2026-03-07: dominant no-std `nan_dp_schedule_ndc_start(arg=1)` timer executes on time, so timer lateness is not the cause

- Added a compact execution-lateness probe in:
  - `vendor/esp-rtos-0.2.0/src/esp_radio/timer_queue.rs`
  - exported via:
    - `vendor/esp-rtos-0.2.0/src/lib.rs`
    - `vendor/esp-radio-0.17.0/src/lib.rs`
  - logged from:
    - `src/firmware/storage/upload/wifi/connect/boot_scan_diag.rs`
- The probe records, for the most recently executed no-std timer callback:
  - callback pointer / arg
  - scheduled due timestamp
  - actual execution timestamp
  - timeout used when armed
  - execution lateness (`exec_at - due_at`)
  - max observed lateness in the bounded run
- Rebuilt, generated a merged image, and flashed successfully via `esptool.py write_flash`.
- Captured bounded log:
  - `logs/boot_scan_only_diag_timerlateness_20260307_berlin.log`

Key evidence from the log:
- after the first direct IDF `NULL` scan:
  - `timer_exec_diag ... last_callback_ptr=0x40173184 last_arg_ptr=0x1`
  - `last_timeout_us=120000`
  - `last_lateness_us=214`
  - `max_lateness_us=217`
- after the direct IDF explicit broad scan:
  - same dominant callback family:
    - `last_callback_ptr=0x40173184 last_arg_ptr=0x1`
  - still effectively on-time:
    - `last_timeout_us=120000`
    - `last_lateness_us=212`
    - `max_lateness_us=217`
- after the wrapped Rust broad scan:
  - same callback family remains dominant:
    - `last_callback_ptr=0x40173184 last_arg_ptr=0x1`
  - still near due time:
    - `last_timeout_us=120000`
    - `last_lateness_us=249`
    - `max_lateness_us=305`
- all three scans still fail with zero APs in the same run:
  - direct IDF `NULL`: `scan_id=128 count=0`
  - direct IDF explicit: `scan_id=129 count=0`
  - wrapped Rust: `scan_id=130 count=0`

Conclusion:
- the dominant `nan_dp_schedule_ndc_start(arg=1)` timer family is not misfiring due to gross
  no-std scheduler/timer lateness
- observed lateness is only a few hundred microseconds against a `120000 us` timeout
- so the timer subsystem is close enough to spec for this branch
- the remaining target is the semantic state/path that causes this timer family and surrounding
  no-std Wi-Fi runtime to produce `ScanDone(count=0)`, not timer jitter or delayed callback
  execution
