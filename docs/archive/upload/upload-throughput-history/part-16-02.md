## 2026-03-06: forcing `ps=0` and `country=CN/manual` in working C / ESP-IDF does not break scan

- Added diagnostic toggles to the C control app:
  - `CONFIG_WIFI_CONTROL_FORCE_PS_NONE`
  - `CONFIG_WIFI_CONTROL_FORCE_COUNTRY_CN_MANUAL`
  - `CONFIG_WIFI_CONTROL_FORCE_MAX_TX_POWER_80`
- First direct-IDF attempt with all three toggles proved:
  - `ps=0` and `CN/manual` latched successfully
  - pre-start `esp_wifi_set_max_tx_power(80)` aborts with
    `ESP_ERR_WIFI_NOT_STARTED`, so that knob is not valid in that call order
  - log: `logs/esp_idf_wifi_control_scan_state_match2_20260306_berlin.log`
- Reran with only:
  - `CONFIG_WIFI_CONTROL_FORCE_PS_NONE=y`
  - `CONFIG_WIFI_CONTROL_FORCE_COUNTRY_CN_MANUAL=y`
  - `CONFIG_WIFI_CONTROL_FORCE_MAX_TX_POWER_80=n`
  - log: `logs/esp_idf_wifi_control_scan_state_match_ps_country_20260306_berlin.log`

Key evidence:
- latched state:
  - `wifi:Set ps type: 0`
  - `wifi:(2.4G)set country: cc=CN schan=1 nchan=13 policy=1`
  - `pre_scan_driver_state ... ps=0 ... cc=CN. ... policy=1 ...`
- scan still succeeded:
  - `scan_complete total_ap_count=7 returned_ap_count=7`

Conclusion:
- `ps=0` plus `country=CN/manual` is **not** sufficient to reproduce the
  no-std `esp-radio` blackout on the working C / ESP-IDF control path
- the visible pre-scan deltas are therefore correlated but not yet causal
- root-cause focus should move deeper again:
  - lower-level runtime differences in the no-std `esp-radio` path
  - not just the visible power-save or country policy state

## 2026-03-06: queue task roles resolved

- Added short task-role storage to the no-std task object in:
  - `vendor/esp-rtos-0.2.0/src/task/mod.rs`
  - initialized for created tasks from the scheduler `name`
  - main task labeled as `main`

  - `src/firmware/storage/upload/wifi/connect/boot_scan_diag.rs`
- Reran bounded boot scan:
  - `logs/boot_scan_only_diag_taskroles_20260306_133550.log`

Key evidence:
- dominant queue remains a single queue handle:
  - `queue_ptr=0x3ffb5d30`
- sampled sender on that queue is the `main` task:
  - `queue_send_first_task_role=main`
  - first six sampled sends all `task_role=main`
- receiver on that queue is the `wifi` task:
  - `queue_recv_first_task_role=wifi`
  - receiver stays stable through the failing window
- later send-side churn reaches the `timer` task on the same queue:
  - after direct IDF compare:
    - `queue_send_last_task_role=timer`
    - `queue_send_task_changes=53`
- thread-semaphore path still stays pinned to `main`:
  - `thread_sem_first_task_role=main`
  - `thread_sem_last_task_role=main`
  - `thread_sem_task_changes=0`

Conclusion:
- the failing queue contract is now pinned more concretely:
  - `main` sends to the dominant queue
  - `wifi` receives from it
  - later queue sends also come from `timer`
- the next highest-value root-cause target is the `timer -> queue -> wifi`
  interaction on that dominant queue, not semaphore identity and not queue plurality

  - after Rust scan:

    - `queue_send_last_item_word0=0x00000007`

- by the later failing-window checkpoint, the sender role for that last payload is `timer`

Conclusion:
- the dominant queue is carrying a compact `8-byte` message shape that looks like
  a small tag plus pointer payload
- the next best root-cause step is to map those `word0` tags (`6`, `7`) and pointed
  objects to the timer-side producer path, then verify whether that timer traffic is
  expected or anomalous in the failing scan window
