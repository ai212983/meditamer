## 2026-03-06: timer callback resolved to `cnx_connect_timeout`

- Added timer-compat last-callback snapshot in:
  - `vendor/esp-radio-0.17.0/src/compat/timer_compat.rs`
  - exposed via `vendor/esp-radio-0.17.0/src/lib.rs`
  - logged from `src/firmware/storage/upload/wifi/connect/boot_scan_diag.rs`
- Reran bounded boot scan:
  - `logs/boot_scan_only_diag_timerdiag_20260306_134431.log`

Key evidence:
- later failing-window timer bridge state:
  - `last_callback_ptr=0x40183fc0`
  - `last_arg_ptr=0x0`
  - `last_arm_us=120000`
- resolved callback symbol from the built ELF:
  - `0x40183fc0 = cnx_connect_timeout`
  - obtained via local Xtensa toolchain symbol lookup / disassembly on
    `target/xtensa-esp32-none-elf/debug/meditamer`
- disassembly shows `cnx_connect_timeout` immediately calls:
  - `ieee80211_timer_process`
  - with `a10 = 7`, `a11 = 0`, `a12 = 0`

Conclusion:
- the later `timer -> wifi` queue traffic is no longer an anonymous timer source
- it is specifically tied to the Wi-Fi connection-timeout callback path
- the observed last queue payload `word0=0x00000007` is consistent with the callback’s
  `ieee80211_timer_process(..., 7, ...)` call shape
- next step should focus on this connection-timeout timer family and the `ieee80211_timer_process`
  queue messages it generates during the failing scan window

## 2026-03-06: dominant `word0=6` queue message resolved to `ieee80211_ioctl` control traffic

- Added a bounded pointee snapshot for the dominant queue payload in:
  - `vendor/esp-radio-0.17.0/src/common_adapter.rs`
  - `src/firmware/storage/upload/wifi/connect/boot_scan_diag.rs`
- Reflashed and captured:
  - `logs/boot_scan_only_diag_pointee_20260306_1400.log`

Key evidence:
- after the Rust scan, the dominant queue still shows:
  - `queue_send_last_item_word0=0x00000006`
  - `queue_send_last_item_word1=0x3ffbe124`
- the pointee behind that queue item resolves to:
  - `queue_send_last_item_pointee_word0=0x0000035a`
  - `queue_send_last_item_pointee_word1=0x40180768`
- the built ELF resolves `0x40180768` to:
  - `wifi_clear_ap_list_process`
- disassembly confirms the `word0=6` event type is posted by:
  - `ieee80211_ioctl`
  - specifically `pp_post(6, ioctl_ptr)` at `40181bf1`
- `esp_wifi_scan_start` itself constructs an ioctl object and calls:
  - `ieee80211_ioctl`
  - but the last main-side control item sampled by the end of the Rust scan is
    the later `wifi_clear_ap_list_process` ioctl, not the initial
    `wifi_scan_start_process` object

Conclusion:
- the main-side `word0=6` queue traffic is now pinned to the Wi-Fi control/ioctl
  path, not generic queue noise
- the sampled `word1` pointer is a queued ioctl object whose handler pointer can
  be resolved from the built ELF
- by the end of the failing Rust-scan window, the last such control item is
  `wifi_clear_ap_list_process`
- this means the scan-start control path is active and queue delivery is working;
  the blackout still occurs later, before scan results materialize

Next step:
- capture a short ring of `word0=6` pointee handlers rather than only the last
  one, so the control-command sequence around `esp_wifi_scan_start` can be
  compared against the later timer-driven `word0=7` traffic in the same failing
  window

## 2026-03-06: early `word0=6` control-command sequence captured

Key evidence:
- the first six sampled `main -> wifi` dominant queue sends all remain:
  - `item_word0=0x00000006`
- their pointee handler addresses resolve to this control-command sequence:
  1. `0x40180058` -> `wifi_set_mode_process`
  2. `0x40180648` -> `wifi_start_process`
  3. `0x40181338` -> `wifi_ipc_process`
  4. `0x40181018` -> `wifi_get_channel_process`
  5. `0x40180e24` -> `wifi_get_protocol_process`
  6. `0x40180928` -> `wifi_get_scan_params_process`
- by the end of the Rust scan, the last sampled main-side control item has moved
  to:
  - `0x40180970` -> `wifi_clear_ap_list_process`
- the late timer-side `word0=7` queue path still resolves to:
  - `0x401842a4` -> `cnx_connect_timeout`

Conclusion:
- the no-std `esp-radio` control-command queue path is active and ordered through
  a normal-looking startup/query sequence before scan completion
- failure is therefore not explained by the control/ioctl path being absent,
  stuck, or obviously mis-sequenced at the coarse command level
- the remaining gap is between this control-command sequence and the later timer
  family: scan completion still reports `count=0`, and the timer-side
  `cnx_connect_timeout` path begins arriving on the same queue afterward

Next step:
- keep the current command-sequence diagnostic and add a bounded ring for the
  later `word0=7` timer messages as well, so subtype/object evolution on the
  timer side can be compared against the healthy control-command sequence

## 2026-03-06: recent-send ring shows timer-side `word0=7` messages are structurally different

- Added a rolling last-six send ring in:
  - `vendor/esp-radio-0.17.0/src/common_adapter.rs`
  - `src/firmware/storage/upload/wifi/connect/boot_scan_diag.rs`
- Reflashed and captured:
  - `logs/boot_scan_only_diag_timerring_20260306_1407.log`

Key evidence:
- after the Rust scan, the recent dominant queue tail includes:
  - `ordinal=43 task_role=timer item_word0=0x00000007 pointee_word1=0x00000000`
  - `ordinal=46 task_role=timer item_word0=0x00000007 pointee_word1=0x00000000`
  - interleaved with `wifi`-task items:
    - `item_word0=0x00000010`
    - `item_word0=0x00000000`
  - and the last `main`-task item:
    - `ordinal=47 item_word0=0x00000006 pointee_word1=0x40180cc4`
    - `0x40180cc4 -> wifi_clear_ap_list_process`
- after the direct-IDF compare, the recent tail similarly includes:
  - `ordinal=84 task_role=timer item_word0=0x00000007 pointee_word1=0x00000001`
  - `ordinal=87 task_role=timer item_word0=0x00000007 pointee_word1=0x00000001`
- the current build still resolves the main-side sampled control handlers to:
  - `wifi_set_mode_process`
  - `wifi_start_process`
  - `wifi_ipc_process`
  - `wifi_get_channel_process`
  - `wifi_get_protocol_process`
  - `wifi_get_scan_params_process`
- the timer bridge callback remains:
  - `0x401845f8 -> cnx_connect_timeout`

Conclusion:
- the timer-side `word0=7` messages are not shaped like the main-side
  handler-bearing ioctl objects
- on this path, the main-side `word0=6` items continue to carry handler pointers,
  while the timer-side `word0=7` tail carries tiny state-like payloads
  (`pointee_word1 = 0 or 1`)
- this strengthens the current boundary:
  - the coarse control/ioctl path is healthy
  - the later timer-driven queue traffic is a different message family
  - the next root-cause target should be the semantic meaning of those timer-side
    `word0=7` payload states and their relation to `ScanDone(count=0)`

Next step:
- instrument the timer-side `word0=7` message producer/consumer contract one
  level deeper, specifically the small payload object/state that follows
  `cnx_connect_timeout -> ieee80211_timer_process -> pp_post(7, ...)`

## 2026-03-06: timer-side tail confirmed as stable `(subtype=8, state=0|1)` payload

- Extended the queue sample/ring diagnostics to capture both pointee words in:
  - `vendor/esp-radio-0.17.0/src/common_adapter.rs`
  - `src/firmware/storage/upload/wifi/connect/boot_scan_diag.rs`
- Reflashed and captured:
  - `logs/boot_scan_only_diag_timerstate_20260306_1414.log`

Key evidence:
- main-side `word0=6` sampled ioctl objects still show handler-bearing shape:
  - `pointee_word0` in the `0x0301..0x036d` range
  - `pointee_word1` resolving to handler pointers such as
    `wifi_set_mode_process`, `wifi_start_process`, `wifi_ipc_process`,
    `wifi_get_channel_process`, `wifi_get_protocol_process`,
    `wifi_get_scan_params_process`, `wifi_clear_ap_list_process`
- timer-side recent tail entries are now explicit:
  - after Rust scan:
    - `task_role=timer item_word0=0x00000007 pointee_word0=0x00000008 pointee_word1=0x00000000`
  - after direct-IDF compare:
    - `task_role=timer item_word0=0x00000007 pointee_word0=0x00000008 pointee_word1=0x00000001`
- interleaved `wifi`-task tail entries remain:
  - `item_word0=0x00000010`
  - `item_word0=0x00000000`

Conclusion:
- the timer-side `word0=7` queue family is now pinned to a compact state object
  with stable first word `8` and a second-word state that changes from `0` to `1`
  across the failing window
- this is materially different from the handler-bearing ioctl objects used by the
  healthy main-side `word0=6` control path
- the next root-cause target is therefore no longer “which queue path is used”;
  it is the semantic meaning of timer payload `(8,0)` vs `(8,1)` and how that
  transition relates to `ScanDone(count=0)` and the first connection-timeout loop

## 2026-03-06: timer registration/arm history is dominated by the `nan_dp_schedule_ndc_start` family

- Extended timer-compat diagnostics with recent `setfn` / `arm` rings in:
  - `vendor/esp-radio-0.17.0/src/compat/timer_compat.rs`
  - `src/firmware/storage/upload/wifi/connect/boot_scan_diag.rs`
- Reflashed conservatively (`espflash --no-stub -B 115200`) and captured:
  - `logs/boot_scan_only_diag_timerring2_20260306_berlin/boot_espflash_monitor.log`

Key evidence:
- after the first direct-IDF compare:
  - `timer_compat_setfn_recent ... callback_ptr=0x40172174 arg_ptr=0x1`
  - `timer_compat_arm_recent ... callback_ptr=0x40172174 arg_ptr=0x1 us=120000 repeat=false`
  - those same `0x40172174` arm entries dominate the full recent arm ring
- after the Rust scan:
  - recent arms remain dominated by `0x40172174`
  - alternating args are now visible:
    - `callback_ptr=0x40172174 arg_ptr=0x1 us=20000`
    - `callback_ptr=0x40172174 arg_ptr=0x0 us=10000`
- in the same run:
  - `last_callback_ptr=0x40184c28`
  - `0x40184c28 -> cnx_connect_timeout`
  - but that callback does not dominate the recent arm ring
- symbol resolution for the current build shows:
  - `0x40172174 -> nan_dp_schedule_ndc_start + 0x64/+0x68 region`
  - `0x4017881c -> ieee80211_rfid_locp_recv`
  - `0x40184c28 -> cnx_connect_timeout`

Conclusion:
- the timer traffic active during the zero-scan window is not primarily the connect-timeout path
- the recurring arm pattern is dominated by a callback in the `nan_dp_schedule_ndc_start` family,
  with arg/state toggling between `1` and `0` and short `20 ms` / `10 ms` re-arm intervals after
  scan start
- root-cause focus should now move from generic “timer-side queue traffic” to the specific
  `nan_dp_schedule_ndc_start -> ieee80211_timer_process(7, ...) -> (7,8,0|1)` family
