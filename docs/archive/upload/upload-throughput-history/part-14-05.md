## 2026-03-06: setup-time Wi-Fi drop/reinit regressed serial/boot liveness

Objective:

- test whether the app's early Wi-Fi initialization timing is part of the
  blackout by forcing a full setup-time `wifi::new -> drop/deinit -> wifi::new`
  cycle before the upload network stack is constructed.

Change:

- added compile-time diagnostic knob:
  - `MEDITAMER_WIFI_SETUP_REINIT_DIAG`
- behavior:
  - during `src/firmware/storage/upload/mod.rs` setup, if enabled:
    - build the first Wi-Fi controller/interfaces with `esp_radio::wifi::new`
    - immediately drop them (triggering esp-radio Wi-Fi deinit)
    - rebuild Wi-Fi once with a fresh `WIFI::steal()` handle before
      `embassy_net::new(...)`
  - default remains `off`

Artifacts:

- variant flash workspace:
  - `logs/boot_runtime_diag_setupreinit_20260306_090944/`
- captured failure artifact:
  - `logs/boot_runtime_diag_setupreinit_20260306_090944/boot_espflash_monitor.log`

Observed:

- the setup-reinit variant flashed successfully.
- after flash, the board no longer behaved like the prior blackout baseline:
  - direct serial probe produced no UART output at all
    (`serial_probe.log` stayed zero bytes)
  - direct first-start command capture also stayed zero bytes
    (`start_from_waiting.raw.log` stayed zero bytes)
  - `espflash monitor --before default-reset --after hard-reset` failed to
    reconnect/reset cleanly:
    - `Error: espflash::connection_failed`
    - `Failed to connect to the device`
- a follow-up control reflash attempt with the knob disabled did not complete
  promptly after this variant, so the device entered a worse serial/bootloader
  interaction state than the original discovery-blackout symptom.

Conclusion:

- setup-time full Wi-Fi drop/reinit is not a promising blackout fix path in
  this stack.
- even as a diagnostic-only experiment, it appears to regress device liveness
  more severely than the original issue.
- keep `MEDITAMER_WIFI_SETUP_REINIT_DIAG` default `off` and treat the variant as
  rejected unless a later physical recovery and controlled repro prove
  otherwise.

## 2026-03-06: official C/ESP-IDF lifecycle comparison points at esp-radio-specific risk

Objective:

- compare the current Rust `esp-radio` Wi-Fi bring-up path against the mature
  official C/ESP-IDF lifecycle to decide whether more Rust-side recovery
  permutations are justified, or whether we need a C control to separate
  stack-specific behavior from generic ESP-IDF behavior.

Reference points:

- official C scan example:
  - `.embuild/espressif/esp-idf/v5.2.2/examples/wifi/scan/main/scan.c`
- official C station example:
  - `.embuild/espressif/esp-idf/v5.2.2/examples/wifi/getting_started/station/main/station_example_main.c`
- official C Wi-Fi init/deinit test:
  - `.embuild/espressif/esp-idf/v5.2.2/components/esp_wifi/test_apps/wifi_function/main/test_wifi_init.c`
- current Rust stack:
  - `~/.cargo/registry/src/.../esp-radio-0.17.0/src/wifi/mod.rs`

Observed:

- official C STA/scan lifecycle is the expected high-level ESP-IDF pattern:
  - `nvs_flash_init()`
  - `esp_netif_init()`
  - `esp_event_loop_create_default()`
  - `esp_netif_create_default_wifi_sta()`
  - `esp_wifi_init(&cfg)`
  - `esp_wifi_set_mode(WIFI_MODE_STA)`
  - optional `esp_wifi_set_config(WIFI_IF_STA, ...)`
  - `esp_wifi_start()`
  - scan/connect from there
- official C tests also enforce the deinit contract:
  - `esp_wifi_deinit()` while started returns `ESP_ERR_WIFI_NOT_STOPPED`
  - only `esp_wifi_stop()` followed by `esp_wifi_deinit()` is accepted
- current Rust `esp-radio` path differs materially:
  - `wifi_init()` calls `esp_wifi_init_internal(...)`
  - immediately forces `esp_wifi_set_mode(WIFI_MODE_NULL)`
  - initializes supplicant explicitly
  - registers custom STA/AP RX callbacks directly
  - later `wifi::new(...)` applies country and power save
  - `set_config(...)` sets mode/config/protocols
  - `WifiController::drop` always performs Wi-Fi deinit
  - the stack does not use `esp_netif`
  - `esp_wifi_restore()` is not usable in this path (`misc_nvs_restore`
    unimplemented in esp-radio)

Implication:

- we should not assume that a failure in this Rust lifecycle directly implies
  the same failure exists in the mature C/ESP-IDF lifecycle.
- the comparison makes the current blackout more suspicious as an
  `esp-radio`/bare-metal integration issue or unsupported recovery surface than
  a generic ESP-IDF Wi-Fi driver defect.

Next discriminating step:

- once the board is physically recovered, run a minimal official-style C/ESP-IDF
  control app on the same hardware and network:
  - first variant: plain scan-only STA startup
  - second variant: simple STA connect example
- interpretation:
  - if C sees APs reliably, prioritize `esp-radio` issue isolation/minimal repro
  - if C also blackouts, shift root cause lower to board/PHY/environment

## 2026-03-06: added repo-local C/ESP-IDF Wi-Fi control app and auto-IDF wrapper

Objective:

- make the official-style C control reproducible inside this repo so the next
  step does not depend on ad hoc copying from `.embuild` examples.

Change:

- added a minimal ESP-IDF app under:
  - `tools/esp_idf_wifi_control/`
- app behavior:
  - default mode is scan-only STA startup
  - if `CONFIG_WIFI_CONTROL_SSID` is configured non-empty, the same app runs a
    simple STA connect flow with bounded retry and timeout logging
- added wrapper:
  - `scripts/device/wifi_control_idf.sh`
  - commands: `build`, `flash`, `monitor`, `fullclean`
  - prefers `IDF_APP_ROOT` if set
  - otherwise auto-selects the newest local install under
    `.embuild/espressif/esp-idf/v*`
  - now auto-resets a stale non-CMake
    `.embuild/idf_apps/wifi_control/build` directory before `set-target`

Observed:

- installed external ESP-IDF for the C control path at:
  - `$IDF_PATH`
- installed matching external toolchain/python env at:
  - `$IDF_TOOLS_PATH`
- `export.sh` and `idf.py --version` succeed against that external install.

Implication:

- local ESP-IDF `v5.2.2` is old enough that a newer local branch is worth
  testing for the C control path.
- however, that only changes the C control experiment; it does not upgrade the
  Rust `esp-radio` / `esp-hal` stack used by the main firmware.
