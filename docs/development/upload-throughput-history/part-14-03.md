## 2026-03-06: historical good-run comparison does not reveal a visible state delta

Objective:

- compare the new early-state failing-window capture against prior known-good
  discovery evidence to see whether the visible started-state differs.

Evidence compared:

- failing early-state capture:
  - `logs/wifi_discovery_earlystate_20260306_1r_c.log`
  - `pre_start_driver_state` then `first_start_driver_state`
  - immediate `post_start_promisc_diag ... total=0`
- prior known-good discovery runs:
  - `logs/wifi_discovery_debug_step65_protocol_ab_off_1r_20260305_111316.log`
  - `logs/wifi_discovery_debug_step65_protocol_ab_on_1r_20260305_111518.log`
  - both reached `scan_stage end label=active_broad ... result_count=10`
- comparable runtime-state probe shape from Step 65 diagnostics:
  - `logs/wifi_discovery_debug_step65_quick_norecover_listeneroff_1r_20260305_123414.log`
  - `logs/wifi_discovery_debug_step65_promiscdiag_1r_20260305_124102.log`

Observed:

- failing first-start snapshot:
  - `mode=1`
  - `primary=1`
  - `protocol_bitmap=0x07`
  - `cc=CN`
  - `max_tx_power=80`
  - `scan_defaults_rc=0`
  - `scan_active_max=120`, `scan_passive=360`, `scan_home_dwell=30`
- those visible started-state values match the comparable Step 65 runtime-state
  probe logs that were used during earlier discovery investigation.
- meanwhile, prior known-good runs under the same default country/protocol path
  were capable of `active_broad result_count=10`.

Conclusion:

- no obvious visible started-state/config delta has surfaced between the
  failing early-state capture and prior known-good/default-path discovery.
- the remaining dominant hypothesis is now lower-level RX/PHY/radio visibility,
  not a simple misapplied high-level runtime setting.

## 2026-03-06: cold-boot runtime setup and STA config snapshots stay sane in blackout windows

Objective:

- close the remaining gap between cold boot, `set_config`, and `start_ok` by
  proving whether blackout runs are entering start with malformed STA config.

Changes:

- captured a true boot-phase monitor log to repo path:
  - `logs/wifi_boot_monitor_runtime_setup_20260306_berlin_1.log`
- extended early driver-state diagnostics to also log
  `esp_wifi_get_config(WIFI_IF_STA)` snapshots:
  - `pre_start_sta_config`
  - `first_start_sta_config`
- implementation:
  - `src/firmware/storage/upload/wifi/connect/driver_state.rs`
  - `src/firmware/storage/upload/wifi/connect/prepare/prepare_start.rs`

Validation:

- flashed with:
  - `MEDITAMER_WIFI_EARLY_DRIVER_STATE_DIAG=1`
  - `MEDITAMER_WIFI_POST_START_PROMISC_DIAG=1`
  - `MEDITAMER_WIFI_SOFTWARE_RESET_ON_POST_START_PROMISC_ZERO=0`
- boot monitor capture:
  - `logs/wifi_boot_monitor_runtime_setup_20260306_berlin_1.log`
- bounded 1-round discovery capture:
  - `logs/wifi_discovery_sta_config_20260306_1r.log`

Observed:

- cold boot runtime setup is sane before connection task start:
  - `runtime_setup_driver_state ... mode=0 ps=0 protocol_bitmap=0x07 event_mask=0x00000001 cc=CN schan=1 nchan=13`
- failing blackout round still shows sane STA config before and after start:
  - `pre_start_sta_config ... ssid_len=19 scan_method=1 bssid_set=false channel=0 threshold_authmode=4 threshold_rssi=-99 failure_retry_cnt=1`
  - `first_start_sta_config ... ssid_len=19 scan_method=1 bssid_set=false channel=0 threshold_authmode=4 threshold_rssi=-99 failure_retry_cnt=1`
- the same run immediately hits:
  - `post_start_promisc_diag ... total=0`
  - `scan_stage end label=active_broad ... result_count=0`
  - then `failure_class":"discovery_empty","failure_code":201`

Conclusion:

- cold-boot runtime setup is not obviously corrupt.
- the effective STA config presented to IDF is also not obviously corrupt in
  blackout windows.
- that rules out "bad station config applied before start" as the primary
  explanation for current discovery blackout.
- root-cause focus should stay below high-level config:
  - radio/RX bring-up
  - lower-level driver state not surfaced by current getters
  - board/environment visibility that survives clean start and restart

## 2026-03-06: post-start promisc-zero deep reinit did not restore RX visibility

Objective:

- test whether a deeper in-process Wi-Fi reinit can break the blackout without
  requiring full software reboot.

Change:

- added compile-time recovery knob:
  - `MEDITAMER_WIFI_POST_START_PROMISC_ZERO_HARD_REINIT`
- behavior:
  - if `post_start_promisc_diag` returns aggregate `total=0`, firmware now:
    - transitions to `Recovering`
    - stops Wi-Fi
    - applies `reset_wifi_mac()`
    - forces `WIFI_MODE_NULL -> WIFI_MODE_STA`
    - reapplies station config and retries start in the same boot
- implementation:
  - `src/firmware/storage/upload/wifi/connect/recovery.rs`
  - `src/firmware/storage/upload/wifi/connect/promisc_diag.rs`
  - `src/firmware/storage/upload/wifi/connect/prepare/prepare_start.rs`

Validation:

- flashed with:
  - `MEDITAMER_WIFI_EARLY_DRIVER_STATE_DIAG=1`
  - `MEDITAMER_WIFI_POST_START_PROMISC_DIAG=1`
  - `MEDITAMER_WIFI_POST_START_PROMISC_ZERO_HARD_REINIT=1`
  - `MEDITAMER_WIFI_SOFTWARE_RESET_ON_POST_START_PROMISC_ZERO=0`
- bounded 1-round discovery capture:
  - `logs/wifi_discovery_poststart_hardreinit_20260306_1r.log`

Observed:

- each start cycle repeated the same pattern:
  - `post_start_promisc_diag ... total=0`
  - `post_start_promisc_zero_hard_reinit trigger=true`
  - `post_start_promisc_zero_hard_reinit deep_reinit applied reset_wifi_mac=true set_null_rc=0 set_sta_rc=0`
  - next `start_ok`
  - next `post_start_promisc_diag ... total=0`
- no recovery iteration produced:
  - non-zero promiscuous RX
  - non-zero `active_broad` scan results
  - a path past the post-start blackout gate

Conclusion:

- deeper in-process Wi-Fi reinit is not sufficient to restore RX visibility in
  the current blackout state.
- this weakens the hypothesis that stop/start residue, MAC reset, or
  `NULL->STA` mode rebind alone can recover the radio.
- next root-cause focus should move lower than the current controller-level
  recovery path.

## 2026-03-06: RAM-only Wi-Fi storage did not recover discovery blackout

Objective:

- remove flash-backed Wi-Fi persistence from the equation and check whether
  blackout depends on `WIFI_STORAGE_FLASH` state.

Change:

- added compile-time knob:
  - `MEDITAMER_WIFI_FORCE_STORAGE_RAM`
- behavior:
  - call `esp_wifi_set_storage(WIFI_STORAGE_RAM)` during upload runtime setup
  - log `wifi_storage_override` and include storage mode/result in
    `runtime_setup_driver_state`
- implementation:
  - `src/firmware/storage/upload/mod.rs`

Validation:

- flashed with:
  - `MEDITAMER_WIFI_FORCE_STORAGE_RAM=1`
  - `MEDITAMER_WIFI_EARLY_DRIVER_STATE_DIAG=1`
  - `MEDITAMER_WIFI_POST_START_PROMISC_DIAG=1`
- boot monitor capture:
  - `logs/wifi_boot_monitor_storage_ram_20260306.log`
- bounded 1-round discovery capture:
  - `logs/wifi_discovery_storage_ram_20260306_1r.log`

Observed:

- boot monitor confirmed the override latched:
  - `wifi_storage_override mode=ram rc=0`
  - `runtime_setup_driver_state ... storage_mode=ram storage_rc=0 ... protocol_bitmap=0x07 ... cc=CN`
- despite RAM-only storage, the discovery run still hit:
  - `post_start_promisc_diag ... total=0`
  - then zero-result scan entry into the same blackout path
- no non-zero promiscuous RX or non-zero `active_broad` scan evidence appeared
  before the run was stopped.

Conclusion:

- flash-backed Wi-Fi persistence is not the dominant cause of the current
  blackout.
- forcing `WIFI_STORAGE_RAM` removes one plausible NVS-backed explanation, but
  RX visibility still fails immediately after `start_ok`.
- next root-cause work should move lower than storage/config persistence.

## 2026-03-06: raw flash partition inspection and PHY helper link limitation

Objective:

- inspect lower-level stored state (`nvs`, `phy_init`) without adding more
  firmware-side recovery behavior.

Observed:

- direct PHY helper attempt was rejected by the actual link stack:
  - `esp_phy_get_init_data`
  - `esp_phy_release_init_data`
  - `esp_phy_load_cal_data_from_nvs`
- those symbols are declared in headers/bindings but were unresolved at final
  link, so this firmware stack cannot currently use them as simple diagnostics.

Flash-level evidence:

- `espflash checksum-md5` succeeded for both partitions:
  - `nvs` (`0x9000`, `0x6000`): `0x1a649b535a4ae08d173a738eae0bc8eb`
  - `phy_init` (`0xf000`, `0x1000`): `0xf34b8a303a528ee681ef6c943b6c09e0`
- artifact paths:
  - `logs/flash_dumps/nvs_md5_20260306.txt`
  - `logs/flash_dumps/phy_init_md5_20260306.txt`
  - `logs/flash_dumps/phy_init_20260306.bin`
- `phy_init` raw dump was readable and begins:
  - `00 00 00 00 ff ff ff ff ...`
- repeated raw `nvs` reads failed with transport framing errors:
  - `corrupt_data expected 0x1000 bytes but received 0xfe7`
  - `corrupt_data expected 0x400 bytes but received 0x3f0`
  - `corrupt_data expected 0x100 bytes but received 0x0f0`

Conclusion:

- lower-level flash state is not obviously absent: both `nvs` and `phy_init`
  regions respond to MD5 queries.
- direct PHY helper symbols remain unavailable in this firmware link stack, so
  firmware-side PHY inspection is still blocked there.
